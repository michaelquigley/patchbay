- dfx is pinned at v0.1.11, which brings `NodeFlags.Accent` and `LinkFlags.Color`. Selection now shows as a thicker line in a highlight of the block's or link's own hue (Michael's call in the dfx round), so patchbay sets no selection colors of its own.
- The media hues in `internal/ui/palette.go` are starting positions for the placement loop, not settled design: audio steel blue, midi amber, video violet, unknown neutral grey; links at 0.9 opacity.
  - They were chosen against dfx's dark default theme, mid-dark enough that the theme's white title text reads on them as a band. They have not been judged by eye.
  - If the bands read too heavy, the likely next move is a lighter link hue separate from the band hue. One hue per media was the brief.
- Glyphs: `ICON_SETTINGS_INPUT_COMPONENT` (device), `ICON_WEB_ASSET` (application), `ICON_PIANO` (MIDI bridge). The model now exposes `Block.Owner`, so the ui never parses key prefixes for this.
- The hidden-count suffix is a second `Label` on the same row after `imgui.SameLine()`, pushed to `ColTextDisabled`. That is how a single row gets two colors without dfx support; it is detent-safe because both halves are `Label`s.
- `S` snaps to dfx's canvas grid (50), not the model's placement grid (20). Fresh placements land on 20-unit positions until snapped. That's left as is; aligning the two grids is a placement-loop call.
- Fixed, from Michael's hands-on: pressing `S` right after releasing a drag snapped the block back to where the drag started.
  - Cause: dfx runs keyboard actions before the frame is drawn, so the handler read the previous frame's declarations, and that frame's `End` had just committed the move from them.
  - Same class: `C` right after a click centered on the previous selection.
  - Both now read the model's current view (`Refresh`) and the selection set, and the canvas no longer keeps last frame's declarations at all.
  - Rule: an action handler never reads a frame's plan. It reads the model and the canvas's own state, which `apply` has already updated.

## placement loop, round 2 — arrivals in view

- Found live on `seven`: with an arranged workspace panned away from the first layout, plugging in the microKEY put its two blocks at the right edge of the content bounding box, off-screen. They were present and recorded, but invisible. A fresh workspace had hidden this, because its first layout happened to be in view.
- Why the content-bounding-box rule failed: it answered "where is there free space" when the question is "where is the operator looking". With an arranged graph, the right edge of the content is wherever the operator once dragged the rightmost block, which has nothing to do with the current view.
- The new rule:
  - Arrivals go inside the visible canvas rectangle, right-aligned and stacked from the top. They are announced in the status strip, and `N` centers on them (work order decision revised 2026-10-06).
  - The canvas reports the rectangle via `CanvasFromScreen` after each frame. Before the first report, the model uses the remembered pan and zoom at an assumed 800×500 canvas, so startup arrivals also land in the view the window opens onto. Deferring placement until a report was considered and rejected: it would hide new blocks for a frame and complicate every test.
  - Arrivals may overlap existing content in the view. That is accepted: overlap in view beats placement off-screen.
- Announcements skip the graph a connection starts with, so startup and reconnects don't flood the strip. A block that returns to a remembered off-screen position is announced too: it "appeared", and `N` finds it.
- `Model.SetViewport` is presentation input only; nothing about it is stored.

## stage 4 — patching and the inspector

- `CreateLink` and `DestroyLink` take a `session` argument, which the work order's contract does not show. Serials name objects only within one connection session, and only the caller knows which snapshot it acted on. A request against another session fails in the graph rather than resolving reused serials. This follows directly from the session rule settled in stage 3.
- One link lifetime: a create request captures the first link global announced with the proxy's bound id and a serial above the watermark taken at posting (`Graph.maxSerial`). The watermark keeps a pre-existing link that happens to hold that id from being captured.
- Deliberate gap, left as the work order has it: the two-second timeout covers only "no captured link". A captured link that sits below `active`/`paused` and never errors keeps its request pending. It has not been seen; the likely sign would be a pending line in the strip that never clears. If it shows up, extend the timeout to captured-but-unconfirmed rather than inventing a state.
- Link proxies are released at resolution, and the lingering link outlives the proxy, per the link factory's `object.linger` handling. A release can be decided inside the proxy's own callback (an error, removed), so `nativeSession.releaseLink` queues it and `pbWake` destroys queued proxies after the flush. The C callbacks also read `l->conn` before calling Go. Don't "simplify" either back.
- The request history (16 resolved) lives on the graph, not the session state, so the last snapshot of a lost connection, already marked disconnected, still shows the requests the disconnect failed. A reconnect starts an empty table; the ui's request descriptions are keyed by `RequestID`, which the backend never reuses.
- Verified against a real daemon (private, scratchpad socket; two null sinks made with `adapter.auto-port-config`, since there is no session manager): create confirmed active and created here; destroy confirmed on removal; a created link survived closing the connection, and the next connection saw it as observed (`TestLiveLinkRoundTrip`, `TestLiveLinkLingers`, `-tags live`; they skip without the `pbtest-a`/`pbtest-b` sinks). Use `PIPEWIRE_RUNTIME_DIR=rt` rather than `XDG_RUNTIME_DIR` when the window must also reach Wayland.
- Still open for stage 4 acceptance, operator-run:
  - on the desktop: built-in source → USB sink, plus `Delete`, a `pw-link` race, and a vanished-port request, all by eye;
  - on `seven`: microKEY-25 → a REAPER MIDI input, notes received in REAPER, the link surviving Patchbay's close, and observed on relaunch.
- Terminus round 1 advisories, decided with Michael:
  - F1 (docs said patching was unbuilt): fixed.
  - F2: the live-test rule was made true rather than dropped. The live link tests now create their own non-lingering null sinks through `backend.createTestSink` (`testsupport.go`, test-only, on an owner connection), patch only between them, and remove them. Verified on a fresh private daemon: graph identical before and after, no links left.
  - `createTestSink`'s `remove` releases `postMu` before taking the loop lock, because the loop thread takes `postMu` while holding its lock. Holding both is a deadlock.
- F3, behavior change vetoed (Michael): every observed Link global is drawn whatever its state, because hiding a negotiating link would claim a route PipeWire says exists is absent. The state shows in `LinkFlags.Color`: media hue when active, dimmed (0.35) for init, negotiating, allocating, and paused, warning red for error. `paused` is common for links between idle nodes, so an idle graph reads dim; that is the honest picture, not a bug.
- Terminus round 2 blocking findings, decided with Michael:
  - F1, replacement capture: an unbound create records the first link lifetime announced under each id since posting. On bound, that first lifetime is the request's link, captured or failed, and a later holder of the id is never captured. A "gone" set was considered and dropped: a gone lifetime is simply no longer in the object table.
  - F2, queued requests lost on disconnect: `lost()` detaches the transport and drains the queue in one step under `postMu` (`backend.detach`). That closes the window where a post between drain and detach would be queued for nobody.
  - A post made with no connection fails at once via `failNow`, which republishes the current snapshot with the failure appended. The next graph's fold replaces that table, which is fine: it is a new session.
  - The ui refuses link and `Delete` gestures on a stale view into its own `refused` list, shown with the snapshot's requests, so a not-connected gesture is visible without a round trip. The backend's not-connected failure stays as the second line of defense.
- Finding F3 of the same round, metadata matched by id, decided with Michael: `MetadataEntry.SubjectSerial` resolves on arrival after the barrier, and at the latch for entries delivered during enumeration.
  - The latch case exists because the `default` metadata object registers early, so its properties arrive on bind before most nodes are announced. Strict resolve-on-arrival would leave nearly every startup entry unresolved.
  - A removed subject orphans its entries for good (`orphanSubjects`). A pending (pre-latch) subject whose id is removed before the latch is orphaned too, so the latch can't hand it to the id's next holder.
  - With nothing selected, the inspector lists the default metadata object, showing `subject unresolved` rather than omitting such entries. Unresolved subjects are not counted in `Unresolved`, by Michael's call.
- Terminus round 3, decided with Michael:
  - F1, metadata: resolution moved per entry (`object.pending` holds the entries awaiting the latch). The per-subject-id ref map let a new property re-attribute older orphaned entries.
  - F2, `failNow` racing the disconnect: the out-of-graph failure list was proposed and rejected by Michael. Instead the backend has one lock (`backend.mu`) over publication, the posting queue, the current transport, and request ids. `lost()` detaches, fails queued requests, folds, and publishes disconnected in one critical section, and `post()` checks for a connection under the same lock. The separate `postMu` is gone, because keeping it would have needed a lock inside a lock.
  - `mu` must stay a leaf. While it is held the work is slice ops, the atomic store, non-blocking sends, graph folds, and transport `wake` (an eventfd write). Never take the pw loop lock under it: `createTestSink`'s remove releases it first, because the loop thread takes `mu` while holding the loop lock.
  - The no-connection path keeps the request table to the last 16, like a graph. The first race test posted ~900 requests and "lost" most of them to that bound, not to the race.
  - F3, inspector across a reconnect: `inspectSource` picks the snapshot the drawn view came from. The app retains `lastLive`, and a stale view uses it only on a session and generation match; the request list stays on the current snapshot. Never pass the current snapshot to the inspector for a stale view: during a reconnect it is the new graph.

  - F2: `Close` ends the session through `ts.end("closed")` → `lost("closed")`. The native `end` takes the loop lock first, then `lost` takes `mu`: the only lock order. `closeCurrent` is gone.
  - Michael's instruction for round 5: if terminus raises another connection-lifecycle finding, don't fix it. Write the lifecycle into `backend.md` as a state machine and report back.

The loop thread runs it during flush with the loop lock held; it fails with "not connected" when nothing is current, and with the disconnect reason when lost first.
