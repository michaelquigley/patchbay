## stage 2 — model and workspace

- **Sample vs work order, surfaced not adapted:** the stage 2 acceptance says `seven` adds "four one-port VirMIDI blocks". The alias-prefix rule as the work order states it gives eight. Each of the four VirMIDI ALSA clients (`Virtual Raw MIDI 0-0` … `0-3`) has one capture and one playback port, and blocks split by direction. `TestMidiBridgeBlocks` asserts eight, one port each. If four was meant (in and out together), that is a rule change, not a test change.
- Gaps the identity decision did not cover, filled as follows and pending Michael's read:
  - Ports without `format.dsp` on Video nodes get media `video` in the recognition key; the decision names only audio and midi.
  - Device-backed nodes that are not ALSA PCM (the v4l2 camera on `seven`) key ports by `port.name`, as ALSA does.
  - A block whose identifying name is empty is unkeyed: drawn and movable in session, never matched or recorded. A port with an empty key cannot be hidden by key.
- Record creation is deliberately lazy for ambiguous blocks. An unambiguous new block gets a record at once, so its placement survives. An ambiguous one gets session placement only, and its first gesture allocates an ordinal slot. Creating slots on appearance would add two records per collision per startup forever, since records are never deleted and colliding blocks are never auto-assigned.
- A block presented as new stays new even if its colliding sibling leaves (`match` skips blocks with a session entry). That reads the rule "the record stays in the association chooser until the operator assigns it" literally. Do not "fix" it into a late assignment.
- Any non-live snapshot releases every assignment and the model returns the last live view marked stale. The stage 3 canvas should draw that stale view desaturated rather than an empty or partial connecting graph.
- `Block.Ordinal` is a display label among same-key blocks that have no record, in arrival order (lowest port serial). It is never consulted for assignment.
- Placement heights are estimates (40 header, 20 per port, all ports including hidden ones, so revealing never overlaps). Stage 3 may replace them with dfx's measured sizes.
- The stage 1 acceptance half deferred here (no assignment on a `connecting` snapshot, two same-key candidates arriving in separate snapshots) is `TestNoAssignmentWhileConnecting`.
- Terminus round 1, finding native-identity-1, decided with Michael: identity inputs are typed snapshot fields (`Port.Name`, `Alias`, `AliasPrefix`; `Node.AppName`, `Description`, `Nick`, `DeviceSerial`) and the model never reads `Props`. `AliasPrefix` is only the parsed text; deciding that it names the ALSA client is the model's job. The nick fallback for titles is applied in the model, not folded into the snapshot. `DeviceSerial` resolves `device.id` at the node's announcement, not at fold time, to keep the serial-1 rule (no late resolution). Michael chose this over the fold-time wording when the conflict was raised. Follow-up, also Michael's call: that miss must not fall back silently. `Node.HasDevice` (device.id present) decides the `node:` class whether or not the device resolved, and a node with `HasDevice` and no `DeviceSerial` counts in `Unresolved`. A device announced after its node still does not resolve it (no late resolution); the miss is logged once, at the node's announcement.
- Terminus round 1, finding stale-refresh-1, decided with Michael: the model keeps the state and reason of the last snapshot it was handed; `m.last` holds only views built from live snapshots and is never returned while not live. One builder (`staleView`) makes every non-live view, carrying `Reason` and `LiveGeneration`. The stage 3 ui must take a fresh view each frame and never cache one; the stale flags are only true for the frame they were built in.
