## stage 2 — model and workspace

- **Sample vs work order, surfaced not adapted:** the stage 2 acceptance says `seven` adds "four one-port VirMIDI blocks". The alias-prefix rule as the work order states it gives eight. Each of the four VirMIDI ALSA clients (`Virtual Raw MIDI 0-0` … `0-3`) has one capture and one playback port, and blocks split by direction. `TestMidiBridgeBlocks` asserts eight, one port each. If four was meant (in and out together), that is a rule change, not a test change.
- Gaps the identity decision did not cover, filled as follows and pending Michael's read:
  - Ports without `format.dsp` on Video nodes get media `video` in the recognition key; the decision names only audio and midi.
  - Device-backed nodes that are not ALSA PCM (the v4l2 camera on `seven`) key ports by `port.name`, as ALSA does.
  - A block whose identifying name is empty is unkeyed: drawn and movable in session, never matched or recorded. A port with an empty key cannot be hidden by key.
- Record creation is deliberately lazy for ambiguous blocks. An unambiguous new block gets a record at once, so its placement survives. An ambiguous one gets session placement only, and its first gesture allocates an ordinal slot. Creating slots on appearance would add two records per collision per startup forever, since records are never deleted and colliding blocks are never auto-assigned.
- A block presented as new stays new even if its colliding sibling leaves (`match` skips blocks with a session entry). That reads the rule "the record stays in the association chooser until the operator assigns it" literally. Do not "fix" it into a late assignment.
- Any non-live snapshot releases every assignment and the model returns the last live view marked stale. The stage 3 canvas should draw that stale view desaturated rather than an empty or partial connecting graph.
- `Block.Ordinal` is a display label among same-key blocks that have no record, in arrival order (lowest port serial). It is never consulted for assignment.
- Placement heights are estimates (40 header, 20 per port, all ports including hidden ones, so revealing never overlaps). Stage 3 may replace them with dfx's measured sizes.
- The stage 1 acceptance half deferred here (no assignment on a `connecting` snapshot, two same-key candidates arriving in separate snapshots) is `TestNoAssignmentWhileConnecting`.
- Terminus round 1, finding native-identity-1, decided with Michael: identity inputs are typed snapshot fields (`Port.Name`, `Alias`, `AliasPrefix`; `Node.AppName`, `Description`, `Nick`, `DeviceSerial`) and the model never reads `Props`. `AliasPrefix` is only the parsed text; deciding that it names the ALSA client is the model's job. The nick fallback for titles is applied in the model, not folded into the snapshot. `DeviceSerial` resolves `device.id` at the node's announcement, not at fold time, to keep the serial-1 rule (no late resolution). Michael chose this over the fold-time wording when the conflict was raised. Follow-up, also Michael's call: that miss must not fall back silently. `Node.HasDevice` (device.id present) decides the `node:` class whether or not the device resolved, and a node with `HasDevice` and no `DeviceSerial` counts in `Unresolved`. A device announced after its node still does not resolve it (no late resolution); the miss is logged once, at the node's announcement.
- Terminus round 1, finding stale-refresh-1, decided with Michael: the model keeps the state and reason of the last snapshot it was handed; `m.last` holds only views built from live snapshots and is never returned while not live. One builder (`staleView`) makes every non-live view, carrying `Reason` and `LiveGeneration`. The stage 3 ui must take a fresh view each frame and never cache one; the stale flags are only true for the frame they were built in.

## stage 3 — the canvas

- Not yet seen by a human: the window was smoke-run against the eleven sample, but no screenshot tool exists on the desktop (Wayland, no grim/gnome-screenshot), so layout, legibility, and the desaturated stale look are unverified by eye. (The libdecor failure noted here at first was a patchbay bug, not the environment; see the stage 3 decorations entry below.)
- For the hands-on placement loop:
  - Block sizes are estimates in `internal/model/reconcile.go`: 40 header, 20 per port, 8 units per character of the longest title or label, plus 48. The canvas measures real sizes, but nothing feeds them back.
  - If blocks overlap or gape, tune those constants first. The other route is feeding dfx-measured sizes into placement, which means a new model input.
  - dfx's canvas grid is 50; the model snaps to 20. Neither is wrong; they just don't line up.
- Stacking order (`NodeRaised`) is session-only; the workspace has no field for it. Raised blocks fall back to view order on restart.
- `--workspace <file>` is a stage 3 decision, not in the work order: it selects the workspace file for either mode. Without it, `--sample` defaults to `sample-workspace.yaml` beside the live workspace, so a capture's records never land in the workspace the live graph uses. The work order said nothing about where sample mode writes. Both calls are mine and open to reversal; Michael accepted the flag at the round 1 advisory triage.
- The ui reconciles every frame and never caches a view, per the stage 2 rule. If that ever shows in a profile, cache on (snapshot pointer, model revision), not on the snapshot alone.
- A stale view locks the canvas (`SetLocked`) so a drag can't snap back when the model refuses the move. Selection and navigation stay live.
- `H` hides selected blocks only; dfx has no pin selection, so port hiding waits for the inspector (stage 4). `Delete` is unregistered rather than a no-op.
- Still open for stage 3 acceptance, by hand on the desktop:
  - arrange, close, and reopen against the eleven sample;
  - switch to the restart sample with the same workspace;
  - check the monitor filter's hidden counts on the remote-desktop inputs;
  - toggle Show hidden;
  - plug and unplug a USB audio device live. The model halves of all of these are fixture tests already.
- Terminus round 2, finding reconnect-recognition-1, decided with Michael: `Snapshot.Session` numbers the connection, and the model releases every assignment when a snapshot's session differs from the one its assignments were made under, live or not. Before this, release depended on the ui happening to see a non-live snapshot, and a stalled frame loop could miss the whole disconnect. The rule that follows, now stated in `backend.md`: events are lossy hints, and anything that must be correct comes from the snapshot. Stage 4's request handling has to obey it too: a request's outcome event can be dropped, so the status strip's request list needs a snapshot-side source, not only `RequestResolved`.
- Terminus round 2, finding reconnect-selection-1, decided with Michael: canvas selection and stacking order are session-scoped by construction. They are held by `BlockID`, which carries a serial, and `canvas.track` clears both when a view from a new connection session arrives. That is correct for v1. If stacking order ever has to survive a restart, the route is keying it by record key for blocks that have one. Do not remove the reset.
- Stage 3 decorations defect, fixed: on Wayland the window intermittently came up without decorations, logging "Failed to load plugin 'libdecor-gtk.so': failed to init".
  - Cause: `cmd/patchbay` never called `runtime.LockOSThread`. The main goroutine could migrate off the main OS thread before dfx created the window, `gtk_init_check` then failed inside libdecor's GTK plugin, and GLFW fell back to no decorations. It depended on scheduling, which made clean builds and reruns look like they changed it.
  - The earlier notes were wrong: blaming the desktop's environment, and blaming a stale build.
  - Fix, as baab's `cmd/baab/studio.go` does it: the thread lock is in `init()` of package main, and `ui.Run` creates and runs the window on the calling goroutine.
  - Verified: ten consecutive `--sample` launches, none printing the libdecor line. Decorations by eye still need Michael's confirmation, since I can't screenshot this desktop.
  - The libdecor Cairo plugin is deliberately not installed or loaded: it hides the failure rather than fixing it, per baab's card.
  - Rule carried forward from baab (2026-08-20): a `LockOSThread` in `init` proves nothing unless the UI actually runs on that goroutine. Never move `ui.Run` or `app.Run()` into a spawned goroutine.
