# 2026-10-07 — stage 5, quantum and monitoring

- The profiler interface needs `libpipewire-module-profiler` loaded into the client's own context (pw-top does `pw_context_load_module` for it). Without it, `pw_registry_bind` returns NULL for the Profiler and monitoring silently shows nothing. The load happens in `pb_conn_new`; a failure logs and leaves monitoring unavailable.
- Profiler pods don't wake the loop (`on_profile` calls Go once per profiler object, with no `wake`). At quantum 64 that is 750 pods a second, and waking would fold the graph that often. Summaries are recomputed on the backend tick, which is now 100ms (it was 250ms), and published only when they changed. Don't add a wake to `on_profile`.

- Stage 6, identity against the 2026-10-07 samples. What the samples contradicted, and what was amended (the work order's identity decision records the amendments):
  - **WirePlumber's name counter.** In the 10-02 baseline, seven's built-in, HDMI, S/PDIF, and webcam alsa nodes are named `….3`/`….4`; in every 10-07 capture they are not. The counter is WirePlumber's deduplication suffix, a runtime value. Without amending, a workspace saved from the baseline moved every one of those blocks in the absent and reconnect cases. `deviceNodeName` drops one trailing `.2`–`.99` (no leading zeros) for device-backed classes only.
    - The v4l2 node's trailing `.0` is a USB interface number and is kept.
    - A stray `.N` on a real name maps deterministically, so it stays stable. A false merge can only produce a collision, which presents both blocks as new. It cannot mis-assign.
    - Existing workspaces carry keys with the counter. Those records go absent once, and the blocks come back as new.
  - **Device serial.** `Node.DeviceSerial` is the device object's serial and changes on replug and on profile change (330, then 2609, then 2714 for the Scarlett). The chooser hint and the profile gap use the hardware `device.serial`, now typed as `Device.HardwareSerial`. Records remember it as `device`, which is never matched on. It is learned on first assignment and kept, so an association across devices does not overwrite it.
  - **Auto-records vs the profile case.** Under the old rule, a pro-audio block (new, unambiguous) got its own record at once. After association, that record and the multichannel record (through `also`) both answered to the pro key, so the next return was the mirror case and took neither. A new block with an unheld same-device, same-media/direction record under another key is now held with session placement and `GapSameDevice`.
  - **Not adapted, surfaced:** the brief's "save, reload against the same [two-REAPER] sample: the association holds" contradicts conservative recognition. An association binds a serial for its lifetime, and a new process cannot know which of two identical instances it was. The tests assert the rule: within the session the association holds; after reload with both live, neither takes the record, which stays intact and offered. Decided: the brief was wrong and the lifetime-rule tests stand.
  - **Interpretation, confirmed:** the chooser orders same device first, then the rest. Only records of the block's media and direction are offered, because `Associate` refuses others, so a "then by media and direction" tier would be empty.
  - "Both appear as new with ordinal record keys" was read as display ordinals (#1, #2). A record slot with an ordinal key is created on the first gesture, as before; `TestTwoReaperGesturesKeepSeparateRecords` covers it.
  - All three amendments were accepted as built, and both interpretations confirmed (including display ordinals for "ordinal record keys"). Stage 6 is complete pending live acceptance on seven: the inspector gap text and the chooser's `· same device` marker under a real profile switch.
