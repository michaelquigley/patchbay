# Patchbay — work order

The phase-2 artifact for `patchbay.md` (same directory): the spec translated into packages, contracts, stages, and acceptance criteria. The spec says what Patchbay is and what it must never pretend to know; this document says what gets built, in what order, and how each stage proves itself. Where the spec left an implementation-shaped question open, this document answers it and marks the answer as a work-order decision so review can check the call rather than discover the gap.

The repo is docs-only, so "the spec meets reality" here means the spec meets four things that already exist: the graph samples captured from both studio machines (`samples/`), the dfx NodeCanvas as shipped (`dfx/docs/current/node-canvas.md`), the PipeWire proof of concept (`research/pipewire`), and SessionMixer's topology layer. All four were read for this document.

## Where the spec meets reality

Findings from the samples and the code, in decreasing order of consequence.

1. **Runtime IDs recycle within seconds; `object.serial` is the only runtime-unique handle.** Across the REAPER restart on `eleven`, the new REAPER node came back as node id 59 and client id 173, the same ids the old instance had; only `object.serial` advanced (4485 to 4591). `seven` showed the same (node 198, client 207). REAPER's port ids were reshuffled among its own ports. The backend therefore keys every live object by serial and treats the id as a protocol handle only. The spec's claim that runtime IDs are not identity is stronger than it sounds: they are not even stable instance identity.
2. **The studio runtime is PipeWire 1.0.5 and WirePlumber 0.4.17.** The development desktop runs 1.6.2. The backend targets the 1.0 API surface and nothing newer. Because cgo links `libpipewire-0.3` at build time, binaries are built on the machine they run on. The desktop needs `libpipewire-0.3-dev` installed before stage 1 compiles.
3. **REAPER is one node carrying both media.** It has no `media.class`; it has `client.api = jack`, `media.type = Audio`, `media.category = Duplex`, `node.group = group.dsp.0`, and ports with `format.dsp` of either `8 bit raw midi` or `32 bit float mono audio`. Port names are `in1`, `out1`, `MIDI Input 4`; `port.alias` (`REAPER:in1`) is stable across restart. Port counts differ per machine (48 on `eleven`, 41 on `seven`) and MIDI port numbering follows REAPER's own device enablement. So REAPER's four blocks are derived from ports, exactly as the spec now states for MIDI.
4. **Hardware MIDI is ports on the Midi-Bridge node, with no `port.group`.** The grouping key available is `port.alias`, whose prefix before the first colon is the ALSA client name (`Launchpad Pro 2`, `Scarlett 18i20 4th Gen`, `microKEY-25`, `Midi Through`). `port.name` embeds the USB path and `object.path` embeds the ALSA sequencer client number, both unstable across replug. Block key for bridge MIDI is the alias prefix; port key is the full alias.
5. **The Scarlett identity is in the node name.** `node.name` and `device.serial` carry the USB serial (scrubbed to `SCARLETT18I20` in the checked-in samples; the real serial is on the hardware). The active profile on both machines is `Multichannel Duplex`, exposing 26 channels on the 18i20 and 18 on the 16i16, named `AUX0..AUXn`, with `object.path` giving the ALSA channel index (`alsa:pcm:0:hw:0:capture:capture_3`). The sink node also exposes `monitor_AUXn` output ports flagged `port.monitor`; these are the spec's monitor category. A `pro-audio` profile is also offered; the profile-change sample is still to be captured.
6. **Links REAPER makes are indistinguishable from links Patchbay will make.** REAPER's JACK connections appear as `object.linger = true` links with no `client.id`, the same shape as a link created through the link factory with linger. After the restart, 25 of 45 link ids survived (the non-REAPER ones); REAPER's were recreated with new ids and serials. Provenance for "created here" is in-session memory keyed by serial, nothing more, as the spec requires.
7. **The global forced quantum wins over REAPER's per-node forcing, and release returns to REAPER's value.** `pw-jack -p64` becomes `node.force-quantum = 64`, `node.force-rate = 48000`, `node.lock-quantum = true` on the REAPER node (128 on `seven`). Setting `clock.force-quantum = 256` moved the driver quantum from 64 to 256 on `eleven` and 128 to 256 on `seven` while REAPER ran; setting it back to 0 returned each driver to REAPER's forced value, not to the 1024 default. The Scarlett xrun counters did not move, but two desktop streams on `eleven` took 2 and 4 xruns across the two switches. The quantum control is viable under the real launch method, Automatic means "whatever the clients force", and switching is not glitch-free for followers. No audible notes were recorded; that line in the probe's `meta.txt` is still open.
8. **There is more than one driver, and the driver is not always the interface.** On `seven` the C920 webcam microphone was the driver at 128 with both Scarlett nodes as followers. Scarlett nodes carry `node.driver = true`. The observed quantum is a per-driver fact; the UI shows each driver that has running followers, not one number.
9. **The profiler is present and pw-top's decoding is the recipe.** Both machines expose `PipeWire:Interface:Profiler`. Binding it requires the client to load `libpipewire-module-profiler` into its own context, as pw-top does. pw-top binds it with `PW_VERSION_PROFILER` and parses `SPA_TYPE_OBJECT_Profiler` pods: `info` (count, three cpu loads, xrun count), `clock` (flags, id, name, nsec, rate, position, duration, delay, rate diff, next nsec), and `driverBlock`/`followerBlock` (id, name, prev signal, signal, awake, finish, status, latency, optional xrun count). Quantum is `clock.duration`, rate is `clock.rate.denom`, and a node's xrun count is its block's optional count; the info count is the driver's own and is not a per-follower fallback. One pod arrives per driver cycle, so at quantum 64 that is 750 events per second; aggregation stays on the backend thread.
10. **The proof of concept is a reference for the cgo idioms, not for the loop.** It iterates `pw_main_loop` by hand, syncs once, stores registry-level properties only, never binds objects, and "confirms" link creation by running ten loop iterations. Its reusable parts are the `cgo.Handle` pattern for callbacks, the macro wrappers (`pw_core_sync`, `pw_core_create_object`, `pw_registry_bind`), and the `pw_properties` helpers. Everything about observation, confirmation, settings, and metrics is new.
11. **dfx gives exactly what the spec assumed and no more.** `NodeCanvas[ID]` declares nodes, pins, and links every frame, returns `NodeRaised`, `NodesMoved`, `LinkCreated`, and `SelectionChanged` intents, persists `View{Pan, Zoom}`, skips links whose pins were not declared, and has no delete intent and no context menus. `HCollapse` serves the inspector, `ActionRegistry` the keybindings, and `dd` the workspace file (dfx's own `SaveJSON`/`LoadJSON` show the shape). Patchbay pins dfx at the tag current when stage 1 opens (v0.1.10 at writing).
12. **SessionMixer's topology is importable but heavy.** `sessionmixer/topology` depends on `scarlettctl` and the firmware-pinned profiles; `scarlettctl` provides `GetRouting` and an `EventMonitor` for live control changes; `topology.Device.PCMCaptureEndpoints` carry `RoutingEndpoint.GetCurrentSource()`. The plausible correspondence is `capture_AUXn` to `pcm-capture-(n+1)`, and the spec forbids trusting it until a signal has been pushed through it. `sessionmixer` is not installed on `eleven`, only its `session.yaml`; `scarlettctl` is installed on neither studio machine.

## Work-order decisions

Calls the spec left to planning, made here. Each is reviewable.

- **Samples are fixtures and an offline mode.** `internal/sample` loads a `pw-dump.json` into the same snapshot type the live backend produces. The model tests run over every sample in `samples/`, and `patchbay --sample <dir>` runs the full UI read-only against a sample. This is what lets the canvas, grouping, filtering, and workspace work be built and exercised on the desktop, which has neither REAPER nor a Scarlett. Patching, quantum, and monitoring controls are disabled in sample mode and say so.
- **Snapshot-and-events contract.** The backend owns one `pw_thread_loop`; every libpipewire call happens on that thread under its lock. Callbacks append changes to a pending list; the loop thread folds them into a new immutable `Snapshot` (nodes, ports, links, devices, clients, settings, connection state, generation counter) and publishes it with an atomic pointer swap. The UI reads `Snapshot()` once per frame and never touches a native handle. An `Events` channel carries the discrete things the UI must react to rather than diff: object appeared or vanished (by serial), link state changed, request resolved, connection state changed, metrics summary. Requests (`CreateLink`, `DestroyLink`, `SetForceQuantum`) are posted to the loop thread and return a request id; their outcome arrives only as an event.
- **Confirmation rules.** A `CreateLink` request creates a link proxy; libpipewire reports the global id that proxy was bound to. The request is confirmed when a Link global with that bound id appears, its endpoint port serials equal the serials the request was made for, and its bound info reaches `active` or `paused`; only then is its serial recorded as `created here`. The serial comparison matters because requests travel as protocol ids, and a port id can be recycled between local validation and server processing (on `seven`, port id 129 moved from `REAPER:in1` to `REAPER:in17` across the restart); a link whose endpoints do not match the requested serials is a wrong route, so the request fails visibly and that link, which the bound id proves this process created, is destroyed. A Link global that matches the requested port pair but not the bound id confirms that the route exists and is labeled `observed`, since another client can connect the same pair while the request is pending and link properties cannot tell the creators apart. The request binds to one link lifetime: when the bound global first appears its serial is captured, and confirmation, provenance, and wrong-route cleanup apply to that serial only. The request fails on a proxy error event, an `error` link state, removal of the proxy or of that link before confirmation, or a two-second timeout with no bound global; a later link between the same ports, even under the same reused id, belongs to a new lifetime and is `observed`. `DestroyLink` is confirmed by the global's removal, same timeout. `SetForceQuantum` is confirmed when the settings metadata echoes the value; the resulting driver quantum is a separate observed fact from the profiler and is displayed as such. The canvas draws observed links only; pending and failed requests are shown as events (in the performance panel and, newest, at the toolbar's right end) and in the inspector's request list, never as graph state.
- **Connection states.** `connecting`, `live`, `disconnected`. The backend stays in `connecting` until a core sync round trip has completed after the registry listener was attached and every object enumerated by then has delivered its first bound info; that barrier is when initial observation is complete. Snapshots published before it carry `connecting`, and the model performs no workspace assignment on a `connecting` snapshot, so two colliding candidates that arrive in separate callbacks are judged together once `live` arrives. The same barrier applies after every reconnect. On core error or socket loss the backend publishes `disconnected`, tears down, and retries with backoff from one to ten seconds. On reconnect the new graph is a new graph. Serials come from a per-daemon counter, so a restarted daemon can reuse numbers Patchbay has already seen; the backend therefore clears pending requests, in-session provenance, and all metrics records explicitly on disconnect rather than relying on serials differing, and the model reconciles blocks against the workspace exactly as it does for any returning endpoint. The canvas desaturates and the connection state at the toolbar's right end reads `disconnected` until `live` returns; no link, quantum, or metrics state is shown as current while disconnected.
- **Identity keys.** Two keys, kept apart. The *recognition key* for a block is `(class, media, direction)` where class is one of: `node:<node.name>` for ALSA and other device-backed nodes (`node.name` embeds bus path or USB serial); `app:<application.name or node.name>` for client nodes (`REAPER`, `mpv`); `midi:<alias prefix>` for Midi-Bridge ports. Media is `audio`, `midi`, or `video` from `format.dsp` and the node's media class; direction is `in` or `out` from `port.direction`. Port keys within a block are `port.alias` for client nodes and for Midi-Bridge ports (the alias omits the USB path and ALSA client number that `port.name` and `object.path` carry), and `port.name` for device-backed nodes (ALSA PCM and v4l2), whose names are the stable channel labels. A block whose identifying name is empty is drawn but never remembered, and a port with an empty key cannot be hidden individually; both are rare and both are surfaced in the inspector rather than failed silently. A block with a unique recognition key gets a record when it first appears; a colliding block is placed for the session only and gets a record slot on its first move or hide. The *record key* names a workspace record: the recognition key plus an ordinal slot (`#1`, `#2`) allocated the first time a second record is needed for the same recognition key. Matching always runs on the unsuffixed recognition key; the ordinal is a storage slot and never evidence that a live instance is the one the slot was made for. Association binds one selected live instance (by serial, for its lifetime) to one record. Two live instances producing the same recognition key is the ambiguity case, and it is already in the samples: `eleven` has two gnome-remote-desktop audio-input nodes with identical keys. The rule is that a remembered record is assigned only to an unambiguous match. When a key has more than one live candidate at startup or on return, no candidate takes the record: all are presented as new with ordinal suffixes, and the record stays in the association chooser until the operator assigns it. An assignment made while an instance was the only candidate is kept for as long as that instance is continuously observed (same serial), even if a second instance arrives later; the second is new. When an assigned instance disappears, the record returns to the unassigned pool. The mirror case is handled the same way: one returning instance whose recognition key matches more than one unassigned record takes none of them and is presented as new until the operator associates it. The two-REAPER sample is still to be captured, and this rule is held against it in stage 6.
- **Category classes.** Two in v1, the two the spec names: `video` (any node whose `media.class` contains `Video`, and its ports) and `monitor` (ports with `port.monitor`). Both are hidden by default in a fresh workspace. Classes are computed, never stored, so a port that changes class follows its new class. Further classes wait for use to ask for them.
- **Hidden-connection indication.** For a visible port with links to hidden ports, the pin row's label gains a suffix, `· 2 hidden`, drawn through `Label` so it is detent-safe. A visible block whose own hidden ports carry any links gets a title-bar suffix counting those links, independent of what its visible pin rows show, so a connection on a hidden port is never left without an indication somewhere on the block. Show hidden is a toolbar toggle that declares all blocks and ports for the frames it is on; nothing in the workspace changes.
- **Placement of genuinely new blocks.** A new block is placed in an arrivals column inside the current view: at the right edge of the visible canvas rectangle, stacked downward from the view's top in arrival order, snapped to grid, shifted left only as far as needed to stay fully visible. Existing blocks never move. Every arrival during a session is also announced as an event by name, visible at the toolbar's right end and in the performance panel, and `N` centers the view on the newest arrivals, so a block can never land silently where the operator is not looking. (The first cut placed arrivals at the right edge of the content bounding box; on `seven`, with an arranged workspace, the microKEY landed off-screen and looked absent. Revised 2026-10-06.) A block whose record is remembered goes back to its remembered position regardless of the column. An empty workspace lays the first graph out as two columns, outputs left and inputs right, once; after that the workspace rule applies.
- **Workspace file.** `~/.config/patchbay/workspace.yaml`, written through `dd`, saved on every accepted gesture with a short debounce and on close. Contents: view, category filter state, and a map of block records keyed by the record key, each with its recognition key, position, hidden flag, hidden port keys, and an optional `also:` list of other recognition keys the operator has associated with this record. Records are never deleted by the application. The format has a version field; v1 migrations are out of scope.
- **Affordances.** Per the spec: inspector panel (an `HCollapse` on the right) plus keyboard actions against the canvas selection. `Delete` removes selected links (a request, not a graph edit); `H` hides selected blocks or ports; `Shift+H` toggles Show hidden; `F` zoom to fit; `C` center on selection. The quantum control lives in the performance panel, a left-side `HCollapse` toggled by `P`; the inspector is the right-side panel toggled by `I`. (The first cut put the quantum control and all status in a bottom strip; the strip grew fact by fact across stages 3 to 5 and was replaced by the panel on 2026-10-07. What must never be missed, the connection state and the newest event, stays at the toolbar's right end regardless of the panel.) Association is inspector-only: select the new block, choose "associate with" from the remembered-but-absent records of the same media and direction.
- **Quantum UI.** One control with two states, Automatic and a frame count chosen from the allowed set between `clock.min-quantum` and `clock.max-quantum` as read from settings. Three lines beneath it: requested override (from settings metadata, so an override set by another tool shows too), observed quantum and rate per driver with cycle milliseconds, and the sentence the spec requires about scope. Changing the value posts `SetForceQuantum`; Automatic posts zero.
- **Monitoring semantics.** Per node, the backend keeps the counter from that node's own profiler block; a follower block without a counter is `unavailable`, never substituted with the driver's info counter, which is kept once at driver scope. The record holds `total` (the counter as last seen), `baseline` (the counter at Patchbay open or at the last display reset), and `lastIncreaseAt`. `new = total − baseline`, clamped at zero. A node's first observed counter, whenever it arrives (suspended nodes report nothing until they run), sets `total` and `baseline` together and leaves `lastIncreaseAt` unset, so a late first measurement never shows as new errors. A node is identified by serial, so a replaced node starts a fresh record and its old record is dropped. Profiler blocks name nodes by id, not serial, and follower blocks are buffered under their driver before delivery, so a late block from a departed node can carry the id its replacement now holds; each record therefore stores the `CLOCK_MONOTONIC` time read when the node's registry appearance was received, taken from the backend's own clock and never from a pod, and a block whose pod `clock.nsec` predates that time is dropped before any initialization, since the first pod received after an appearance may itself be a buffered pod from the departed lifetime. That comparison is valid only for drivers whose pod clock is `CLOCK_MONOTONIC` now; live on the desktop the audio driver's is, to the millisecond, while gnome-shell's video driver stamps pods about an hour behind. The cutoff therefore applies per driver only when its pod clock is within one second of the monotonic clock at arrival; other drivers rely on the serial and ordering guards alone, each record shows which mode it is under, and the accepted residual (a stale buffered pod from a replaced same-id node seeding the replacement on an ordering-only driver) is recorded in `docs/current/monitoring.md` (decided 2026-10-07); within a lifetime the record also keeps the `clock.nsec` of the last accepted pod and drops any pod older than it, since pods flush per driver and a node moving between drivers can deliver an older counter after a newer one; only after that ordering check does a counter that goes backwards under the same serial reset that node's baseline to the new value, with a log line. The summary published to the UI is the per-driver quantum and rate, the sum of totals, the sum of new, the most recent increase time, and the per-node list for the inspector. The performance panel labels the sums as counts over currently tracked nodes, not a session history: a replaced node's record is dropped and a rebased counter lowers the sum, both without a display reset. Summaries publish at most ten times a second.
- **cgo layout.** A `pipewire.c`/`pipewire.h` pair in `internal/pipewire` holds every macro wrapper and listener registration; the Go side exports only the callback trampolines. `#cgo pkg-config: libpipewire-0.3`. No Go pointers cross into C memory; one `cgo.Handle` per connection.
- **Scarlett annotations import SessionMixer's topology directly.** `github.com/michaelquigley/sessionmixer/topology` plus `scarlettctl`, behind an `internal/scarlett` package with a one-method interface the inspector consumes (`SourceFor(portKey) (string, bool)`). Extraction into a shared module is the recorded revisit, taken when a second consumer exists. The stage is conditional as the spec says; the condition is written down under stage 7.

## Backend contract

The spec asked for the backend error and lifecycle contract to be made explicit. This is it.

```go
type Conn interface {
    Snapshot() *Snapshot            // immutable; pointer identity changes only when content does
    Events() <-chan Event           // buffered; the UI drains it each frame
    CreateLink(session Session, outPort, inPort Serial) RequestID   // serials mean something only within one session
    DestroyLink(session Session, link Serial) RequestID
    SetForceQuantum(frames int) RequestID   // 0 releases
    ResetMetricsBaseline()
    Close()
}

type Snapshot struct {
    Generation uint64
    State      ConnState                     // connecting | live | disconnected
    Nodes      map[Serial]Node
    Ports      map[Serial]Port
    Links      map[Serial]Link
    Devices    map[Serial]Device
    Clients    map[Serial]Client
    Settings   Settings                      // rate, quantum, min, max, forceQuantum, forceRate
    Metrics    MetricsSummary
}
```

Every object carries `Serial`, `ID` (the protocol id, for requests only), `Props map[string]string`, and the typed fields the model reads (`Node.MediaClass`, `Port.Direction`, `Port.Media`, `Port.NodeSerial`, `Link.OutPort`, `Link.InPort`, `Link.State`). Links and nodes are bound on appearance so `Link.State` and `Node.State` are live, not registry-time. Metadata named `settings` is bound and watched; `default` metadata is bound and exposed read-only for the inspector's policy view. The profiler is bound once and feeds `Metrics`.

Failure tiers: a connect failure at startup is reported in the UI as `disconnected` with the error text and retried, never fatal. A failed request is an event with a reason and never changes the snapshot. A libpipewire error on the loop thread is logged through `dl` and, if it is a core error, becomes a disconnect. Nothing in the backend panics on a malformed property; missing properties yield empty strings and the model treats them as unknown.

## Stages

Each stage is terminus-gated and lands with its `docs/current/` entry. Stage order is dependence order: nothing in stage N needs anything from stage N+1.

### stage 1 — scaffold, backend observation, samples

Repo skeleton per the layout: `go.mod`, Makefile, `AGENTS.md` (house project memory and commit conventions, camelCase file names, lowercase comments, `df/dl` and `df/dd`, `pkg/errors`), `CHANGELOG.md` with an Unreleased slot, Apache 2.0, `cmd/patchbay` with a `dump` subcommand. `internal/pipewire` with the thread loop, registry observation keyed by serial, binding of nodes, ports, links, devices, clients, and the two metadata objects, settings decoding, the snapshot publisher, the event channel, connection states, and reconnect with backoff. `internal/sample` loading every `samples/*/pw-dump.json` into a snapshot. No profiler, no requests yet.

*Accepts when:* `patchbay dump` on the desktop prints the live graph keyed by serial and reprints on change while a device is plugged and unplugged; `systemctl --user restart pipewire` on the desktop produces `disconnected` then `live` with a fresh graph and no crash, and a test with a fake event source proves that a reconnect whose new graph reuses old serial numbers carries over no pending request, provenance entry, or metrics record, and that two same-key candidates delivered in separate callbacks before the sync barrier both reach the model as unassigned; `go test ./internal/sample` loads all seven samples and asserts per-type object counts written into the test from `pw-dump.json` (for the `eleven` baseline: 11 nodes, 150 ports, 45 links, 3 devices); `make test` is green with `go vet`.

### stage 2 — presentation model and workspace

`internal/model`: identity keys, block derivation (class, media, direction), port keys, category classes, the arrivals-column placement rule, and reconciliation of a snapshot against a workspace record set into a `View` of blocks with positions, visibility, and hidden-connection counts. `internal/workspace`: the record type, `dd` load and save, debounce, the version field.

*Accepts when:* fixture tests over the samples prove: REAPER on `eleven` yields four blocks with the same keys before and after restart and every port key maps; the Midi-Bridge on `eleven` yields Launchpad Pro 2, Scarlett 18i20 MIDI, and Midi Through blocks, and on `seven` adds microKEY-25 and eight one-port VirMIDI blocks, one per virtual client per direction, since each virtual port is its own ALSA client and blocks split by direction; Scarlett sinks yield an audio-in block plus a monitor-class out block; `video` and `monitor` classes are computed as expected on all three machines; a workspace saved from the `eleven` baseline and reloaded against the restart sample moves nothing; a block absent from a sample keeps its record; with the Scarlett source and REAPER's `in1` hidden and `in2` visible, `in2` shows a pin-row count and REAPER's title shows a count for `in1`; a bridge port whose `port.name` and `object.path` change (the Launchpad moved to another USB port, synthesized from the `eleven` baseline) while its alias holds keeps its hidden preference. A property-less port never panics.

### stage 3 — the canvas

`internal/ui`: the dfx application, the canvas component declaring blocks and links from the model's `View` each frame, intents applied to the workspace (`NodesMoved` to positions, `NodeRaised` to stacking order, `SelectionChanged` to selection), pan and zoom restored from the workspace at startup with no fit, the toolbar with category toggles and Show hidden, hidden-connection suffixes, and the arrivals column. The toolbar's right end shows connection state. `--sample` mode runs this stage end to end on the desktop. No patching yet: `LinkCreated` is logged and ignored with a status message.

*Accepts when:* against the `eleven` baseline sample, blocks can be arranged, the app closed and reopened, and every block and the view return exactly; switching to the restart sample with the same workspace moves nothing; hiding the monitor class removes the Scarlett monitor ports and the remote-desktop stream's input pins show hidden counts for them; Show hidden reveals and un-reveals without a workspace write; live, plugging a USB device adds its blocks inside the current view at the arrivals edge, announced as an event at the toolbar's right end, and unplugging it leaves everything else still; with an arranged workspace panned away from the first layout, the arrivals are still visible without zooming.

### stage 4 — patching and the inspector

Backend requests (`CreateLink`, `DestroyLink`) with the confirmation rules, request events, and in-session provenance (serials of links this process created). UI: `LinkCreated` validated by the model (same media, output to input, not duplicate, both ports live) then posted; `Delete` on selected links posts destroys; pending and failed requests show as events with reasons; the inspector shows the selected object's properties, its PipeWire ids and serial, link state, provenance (`created here` or `observed`), the `default` metadata that names it, why a block has no workspace record or a port cannot be hidden when that is the case, and the actions (hide, unhide, associate). Keyboard actions registered per the affordance decision.

*Accepts when:* on the desktop a link is created from the built-in source to the USB sink and appears only once its Link global is observed, drawn in its observed state (negotiating or paused dimmed, active normal, error in a warning hue) and never from the request; a request naming a port serial that has already vanished fails with a reason and no phantom link; a synthetic request test in which the target port's id is reused by a different port between validation and the link's appearance fails the request, destroys the wrong-route link, and records nothing as `created here`; a synthetic test in which Patchbay's link is removed before reaching active and another client's link appears under the same id between the same port serials fails the request and labels the replacement `observed`; `Delete` removes the link and the canvas shows its absence only after removal is observed; a link created by another client (`pw-link` from a shell) between the same ports while a Patchbay request is pending is shown as `observed` and Patchbay's own, if it also lands, as `created here`; on `seven`, a MIDI link from microKEY-25 to a REAPER MIDI input is created, REAPER receives notes, Patchbay is closed, and the link remains; relaunching Patchbay shows that link as `observed`, not `created here`.

### stage 5 — quantum and monitoring

Profiler binding and pod decoding per finding 9; per-node metrics records with the baseline semantics; the summary publisher; `SetForceQuantum` through the settings metadata. UI: the quantum control with its three lines, the performance panel's compact metrics (per-driver quantum and rate with cycle milliseconds, total and new xruns, time of last increase), the baseline reset button, and the inspector's per-node metrics list.

### stage 7 — Scarlett annotations (conditional)

Verification first, as an operator task with a written procedure: on `seven`, for every PCM capture channel in turn (18 of them), route a known hardware input to that channel through SessionMixer, play a signal into the input, and record which `capture_AUXn` port carries it; same on `eleven` for all 26. The result is a per-channel table checked into `samples/` alongside the device serial, firmware version, and the PipeWire profile name it was observed under. `internal/scarlett` then annotates exactly the rows in that table and nothing else: a channel with no verified row, a device whose serial has no table, or a PipeWire profile other than the one recorded all yield `unavailable`. Ordering is never used to fill a gap. The package opens the card through `scarlettctl`, detects the hardware profile through `topology`, maps verified port keys to `PCMCaptureEndpoints`, watches control changes through `EventMonitor.Watch` (not `WatchControls`, which swallows failed reads and keeps running), refreshes every verified endpoint itself through `RefreshFromHardware` on each event (the current `Watch` always reports numid 0, so no event names its control), and exposes `SourceFor`. Validity is tracked per channel by the adapter, not by SessionMixer's cache: a channel is valid only after a successful `RefreshFromHardware` and stays valid only while the event monitor is running; any refresh error, a monitor stop or error, or a card close marks every channel invalid, and `SourceFor` returns false for an invalid channel until a fresh successful read. SessionMixer's `GetCurrentSource` is never consulted for an invalid channel, since it returns the last cached value on failure. The inspector shows `hardware source: Analogue Input 1` on verified Scarlett capture ports and `unavailable` otherwise. No pin-label change in v1.

*Accepts when:* on `seven`, routing changes made in SessionMixer appear in the inspector; unplugging the interface or stopping the monitor turns every annotation to `unavailable` rather than leaving the last route showing; a refresh forced to fail in a test does the same, including when the failure is the read triggered by a control-change event while the monitor keeps running; replugging restores annotations only after a successful read; an unverified channel shows `unavailable` with the mapping present.

*The condition:* a channel that fails verification stays `unavailable`; if the table for a machine ends up too sparse to be useful, that machine gets no annotations and the journal says why. If the package exceeds roughly the size of `internal/workspace`, or needs a change to SessionMixer or scarlettctl, stop and bring the scope back to Michael rather than growing the stage.
